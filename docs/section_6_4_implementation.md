# 6.4 Implementation

This section describes how the design from Chapter 4 was realized across the three runtime services. The benchmark project is covered separately in Chapter 5.

## 6.4.1 Backend

The backend is a Spring Boot 4.0.3 application running on Java 25, built with Maven. It exposes the REST API consumed by the frontend, owns all data ingestion, and orchestrates analysis through the LLM service. The codebase is organized in a feature-based layout: each feature (for example, auth, brand, report, post, keyword, feedback) has its own package containing the controller, service, repository, and entity classes that belong to it. This keeps related code colocated and makes feature ownership obvious when navigating the project.

**Domain model.** The data model implements the relational schema from Figure 18 (Company, User, Brand, Keyword, Report, Post, Review, and Feedback) using JPA entities mapped through Hibernate. One deviation from the IS498 design is the primary-key strategy: rather than UUIDs, entities use numeric `Long` IDs generated by PostgreSQL sequences (`@GeneratedValue(strategy = GenerationType.IDENTITY)`). This was chosen for cheaper joins, friendlier debugging, and natural ordering. Database schema evolution is managed by Liquibase: each migration is an explicit changeset that runs at application startup, and the production database is kept in lockstep with the entity model through this mechanism.

**Authentication and authorization.** Authentication is implemented with Spring Security and JSON Web Tokens issued by the `jjwt` library. On login, the backend issues a signed access token that the frontend stores in `localStorage` and attaches to every subsequent API call. The token carries the user's identity and the `companyId` claim, which the service layer uses to scope every database query to the caller's company. Role-based checks (for example, admin-only operations) are layered on top in the same service methods.

**Data ingestion and the PostProvider abstraction.** All post ingestion is owned by the backend and routed through a `PostProvider` abstract class. Two implementations exist: `RedditPostProvider`, which pulls posts from Reddit, and `CsvPostProvider`, which parses an uploaded CSV file (the Upload Custom Dataset feature). Both implementations produce a normalized stream of post objects that the downstream analysis pipeline consumes without knowing or caring where the posts came from. This abstraction is the single most distinctive design point in the backend: it isolates source-specific concerns (OAuth, rate limits, file parsing) inside their respective providers and keeps the analysis pipeline source-agnostic. Adding a new data source in the future is a matter of writing a new subclass of `PostProvider` and wiring it into the provider-selection logic.

**Reddit ingestion.** `RedditPostProvider` authenticates against Reddit's API using the application-only OAuth flow (client credentials, no user account), which grants read access to public submissions. Because this flow is scoped to a single backend process, the access token is cached in memory and refreshed only when it expires; a single token is shared across all ingestion jobs rather than re-fetched per request. Post retrieval uses Reddit's `/search` endpoint with the keywords configured for the brand being analyzed; results are paginated using Reddit's `after` cursor until the user-specified post count is reached. Reddit's HTTP API is called directly via Spring's `RestClient` (no third-party wrapper such as JRAW), which keeps the dependency surface minimal and the request shape transparent in the code.

**Asynchronous analysis pipeline.** The internal job queue shown in the architecture diagram is implemented as a single-worker `ThreadPoolTaskExecutor` (configured in `AsyncConfig`) with a 50-slot in-memory buffer, deliberately kept serial so the LLM service never receives concurrent batches. When a user starts an analysis, the controller delegates to the analysis service, which builds a new `Report` entity in a `QUEUED` state, persists it, and hands the long-running work off to this executor via Spring's `@Async("analysisExecutor")` mechanism, returning control to the caller. The submitted job either begins running immediately or waits its turn behind any analysis already in progress. The worker streams posts to the LLM service in batches and, as each batch returns, persists the per-post results and updates the report's aggregate metrics in place, so the dashboard reflects partial progress while the run is still going. The report's `status` transitions through the states defined in `ReportStatusEnum`, ending in either `COMPLETED` or `FAILED`. The frontend learns about progress by polling a dedicated status endpoint on the report resource, a deliberately simple mechanism that avoids the operational complexity of WebSockets or Server-Sent Events for what is fundamentally a low-frequency check.

**Reports and CSV export.** A "report" in Hawa is a persisted database record, not a generated file. The aggregate metrics and per-post analysis are rendered in-app by the frontend; no PDF or spreadsheet is produced server-side. The one file artifact the backend does emit is a CSV export of the posts underlying a given report, served from `GET /api/reports/{reportId}/export` with the appropriate `Content-Disposition` header. This endpoint is invoked from the posts view in the frontend and writes the filtered post list directly to the response stream.

## 6.4.2 Frontend

The frontend is a single-page application built with React 19 and TypeScript, bundled by Vite 7. Routing is handled by React Router 7, and styling is built on Tailwind CSS 4 with shadcn/ui providing Radix-based primitives (dialogs, dropdowns, popovers) themed against the project's design system. The layout combines a top app bar with a left sidebar that holds the primary navigation, sticky on desktop and collapsing behind a hamburger toggle on mobile.

State management is intentionally minimal: the application uses React's built-in Context API with `useState` and no external state library. Authentication state lives in an `AuthContext` backed by `localStorage`, so a page reload restores the session without forcing the user to log in again, and each outgoing API request carries the JWT in the `Authorization: Bearer` header.

The major views are the dashboard, New Analysis, the reports list, the report detail view, the brand management screen, and the admin pages for user and company management. The report detail view was deliberately built from horizontal bars rather than pie charts or radial layouts, both for the emotion distribution and inside each aspect row, to keep the long tail of low-frequency emotions and aspects readable.

## 6.4.3 LLM Service

The LLM service is a small Python application built on FastAPI (Python 3.12+) that exposes the analysis capability to the backend over HTTP. It owns no data ingestion of its own; its sole responsibility is to accept batches of posts from the backend, classify each one, and return structured results. This boundary keeps the service stateless and trivially horizontally scalable.

The service is provider-agnostic. It talks to the underlying model through the OpenAI Python SDK, which lets the same code drive any backend that exposes an OpenAI-compatible API: Ollama for local development, RunPod for production self-hosting, Groq for managed serverless inference, and Fireworks as an alternate managed backend. The active provider is selected at runtime by the `LLM_PROVIDER` environment variable, and the default model for each provider is a Llama 3.1 8B Instruct variant (`llama3.1:8b` on Ollama, `llama-3.1-8b-instant` on Groq, and the namespaced Fireworks equivalent), with the exact model name overridable through `LLM_MODEL`. Open-source LLMs were a requirement of the academic context, which is why the Llama family was chosen and why the deployment story remained open across self-hosted (RunPod, Ollama) and managed (Groq, Fireworks) backends rather than being locked to a single vendor.

For each post in an incoming batch, the service issues one inference call. The OpenAI-compatible `chat.completions` request uses JSON mode (`response_format={"type": "json_object"}`), and the prompt instructs the model to produce all required fields in a single response: a relevance flag, an irrelevance reason when the post does not count toward brand sentiment, a sentiment score on a 0 to 5 scale in 0.5 increments, a single dominant emotion from the seven-label taxonomy (JOY, ANGER, SADNESS, FEAR, SURPRISE, DISGUST, NEUTRAL), and a single business aspect from the six-label taxonomy (PRODUCT, SERVICE, DELIVERY, PRICING, BRAND, OTHER). The response is parsed and validated with Pydantic, and an enum-coercion layer maps near-miss model outputs (for example, "MAD" to ANGER, "store" to SERVICE) onto the fixed taxonomies before the result is returned to the backend. Within a batch, individual posts are dispatched concurrently with bounded parallelism, and a shared rate limiter governs the outbound RPM and TPM so that managed providers' quotas are not exceeded. The backend then persists each returned classification as a `Review` record linked to its `Post`.
